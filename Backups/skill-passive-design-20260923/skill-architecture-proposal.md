# 技能架构评审草案

日期：2026-09-23。状态：**待用户确认，未实施**。

本轮授权为网上调研、检查现有项目和提出方案。尚未创建技能架构场景、修改技能/战斗代码、安装包或迁移旧场景。本文中的首版范围、默认规则、目录和类型名均为建议，不是已确认需求。

## 已知需求与项目现状

用户希望另建场景验证技能架构，每个技能由范围、Buff 和特殊属性组合，重视复用、扩展、注释和可编辑场景对象；架构由用户定夺后才实施。

项目为 Unity 6000.3.18f1、Entities 1.4.8、URP 17.3.0。Game 已有 ECS 自动射击 Demo，但 CombatPlayer 直接持有血量，CombatProjectile 直接持有伤害，没有通用技能/属性/Buff 结算层。SkillIndicatorDemo 的 CircleSkillPreset、CircleTargeting、CircleIndicatorView 已分别承担圆形配置、距离规则和显示；其配置明确只用于演示，不应直接扩成所有战斗状态的容器。FogOfWar 的批量显隐可作为未来目标过滤输入。

## 路线选择

| 路线 | 优势 | 代价 | 建议 |
| --- | --- | --- | --- |
| A：轻量 GAS 思路 + 项目自有 ECS 执行层 | 配置可组合，生命周期清楚，能沿用 Burst/Jobs 和现有模块边界 | 核心正确性与工具需自行实现、测试 | **推荐** |
| B：直接接入第三方 Unity GAS | 现成配置/编辑工具较多 | 需先验证版本、依赖、存储/执行模型与万级负载；可能增加迁移成本 | 有特定工具诉求再做验证 |
| C：每个技能一个 MonoBehaviour/继承类 | 少量技能起步快 | 相同范围、Buff、冷却与特例容易重复；不适合将逐单位 Update 扩到万级 | 不建议作为长期核心 |

## 推荐组合模型

设计者看到：**技能 = 施法设置 + 范围/目标 + 效果/Buff组合 + 特殊规则 + 表现引用**。

“范围 + Buff”保留为配置入口，但内部明确两个区别：施法距离不等于效果范围；一次性效果不等于持续状态。直接伤害/治疗是即时 Effect，不创建零时长 Buff；灼烧、减速、护盾等需要实例状态的效果才进入 Buff 生命周期。

| 模块 | 配置示例 | 不承担的职责 |
| --- | --- | --- |
| Cast：怎么释放 | 主动/被动触发、瞄准方式、距离、消耗、冷却、前摇、引导、打断规则 | 不直接改血量 |
| Targeting：作用到谁 | 自身/点/方向/单位；阵营、存活、可见性过滤；目标数量和排序规则 | 不由指示器碰撞体决定命中 |
| Area：范围几何 | 圆、扇形、线段/胶囊；中心来源、朝向、半径/角度；一次查询或持续区域 | 不负责 Buff 计时 |
| Delivery：如何到达 | 立即命中、弹体、延迟落地、持续区域 | 不创建另一套伤害公式 |
| Effect：做什么 | 伤害、治疗、应用/移除 Buff、位移请求 | 不实现所有特殊技能分支 |
| Buff：持续状态 | 持续时间、周期、层数、属性修正、状态标签、驱散类别 | 不维护自己的 MonoBehaviour Update |
| Extension：专有机制 | 弹射、击杀重置、传送、召唤等可选择的独立执行器 | 不按技能 ID 在大管理器里堆 if/else |
| Presentation：怎么显示 | 指示器、动画、音效、图标、受击和施法反馈 | 不判定伤害与命中 |

执行顺序建议：

```mermaid
flowchart LR
    A[输入或AI意图] --> B[施法校验与提交]
    B --> C[施法阶段与投递]
    C --> D[范围查询与目标过滤]
    D --> E[效果请求]
    E --> F[按目标结算效果与Buff]
    F --> G[属性与状态更新]
    G --> H[战斗结果]
    H --> I[UI与表现适配器]
```

“命中时/周期时/结束时”可以配置效果列表，并允许简单的标签条件。首版使用明确的阶段与效果列表，不同时建设通用脚本语言、节点编辑器和可任意递归的技能图。真正需要新行为时，增加行为类型、对应数据和专用系统。

## 配置、运行状态和特殊属性

编辑配置建议用 ScriptableObject，类型暂定 SkillDefinition、AreaDefinition、EffectDefinition、BuffDefinition。共享范围/Buff 可被多个技能引用；效果条目可携带倍率、持续时间等局部覆盖，避免为了一个数值复制完整资源。

启动/烘焙阶段校验唯一 ID、引用、周期合法性、参数类型和配置循环，然后生成只读 Blob 定义。运行态单独保存技能等级、冷却、施法阶段、Buff 来源/层数/到期时间。禁止在共享 ScriptableObject 上累加层数或改冷却。

“特殊属性”建议分为三类：

1. 数值参数：穿透次数、弹射次数、弹速、暴击倍率，用有单位和范围的类型化字段。
2. 规则参数：能否暴击、是否受沉默、是否需要可见目标、是否允许移动施法，用明确策略或标签条件。
3. 独有机制：换位、召唤、复制技能，由独立模块提供执行器，仍通过统一效果请求结算。

运行期不用 Dictionary<string, object> 或反射解释特殊属性。编辑期的多态配置可转成紧凑的非托管数据和行为 ID；新增机制可以扩展系统，不承诺任何技能都能纯配置完成。

肉鸽升级建议采用“共享基础定义 + 本角色的参数修正/组合覆盖”，避免一个角色升级后全体共享该技能的角色也变化。首版是否允许局内改变范围形状、投递方式和效果组合，需用户确认；只修改半径/伤害等数值的成本明显更低。

## Buff 与属性的基本合同（建议，待确认）

- Buff 明确区分同名来源是否合并：按定义合并、按定义+来源合并，或独立实例。
- 叠层上限、刷新时长、每层独立到期、周期是否重置分别配置，避免一个“可叠加”开关隐藏多个规则。
- 首版建议实现不叠层/刷新时长、叠层/共用时长、不同来源独立；每层独立计时作为后续扩展，若首版必须则另列验收。
- 基础属性与最终属性分开。建议基础值加平铺修正、再按明确次序计算百分比和最终约束；实际乘区规则是玩法合同，待确认。Buff 到期移除贡献并重算，不用相反加减恢复旧值。
- 生命/资源的即时变化与最大值等派生属性分开。最大生命变化时如何处理当前生命，必须有明确策略。
- 沉默/眩晕等状态由多个来源贡献时使用计数/聚合，移除其中一个来源不能清除剩余效果。
- 同一目标的效果按稳定顺序结算；消耗/冷却在指定提交点只支付一次，失败、取消、打断是否返还写入规则。
- 施法者死亡、目标销毁、Buff 驱散、场景退出和重置都有明确清理路径。延迟效果携带有效来源归属/快照，不盲目读取失效 Entity。
- 伤害等公式区分读取释放时快照还是命中时实时属性。建议字段显式选择，首版示例固定一种并测试。
- 连锁触发携带根施法 ID 和深度，防止反伤/触发递归无界。检测配置循环；运行上限及超限行为须明确，不能静默漏掉正常伤害。

## ECS 与万级目标

共享定义放 Blob；角色活动 Buff 初步用 DynamicBuffer，单位被查询的状态摘要放小型组件。首版按实际 Buff 数测试容量与内存，不给一万单位各预留巨大槽表。弹体/区域单独作为数据实体，保持职责区别。

范围查询先走共享 XZ 空间网格，再做圆/扇形/线段精确测试，避免每个技能逐帧全量扫描。覆盖全图且实际命中一万目标时仍需结算一万次，空间索引不能消除真实命中成本。

并行检测只生成请求；按目标汇总/分区后由有明确所有权的结算阶段写 Buff 和属性，避免多个 Job 同时写同一 DynamicBuffer。结构变化集中经 ECB 播放，跨结构变化重新获取句柄。周期效果按时间点调度，不给每个 Buff 启动协程或 Update。

视觉可以池化和限量，伤害不能因为 VFX 预算耗尽而漏算。显示只订阅低频结果或批量读取摘要，不为每次命中广播托管事件。相同被动 Buff 的无效全量重算使用脏标记减少。

性能验证计划分开统计：活跃目标数、区域/弹体数、实际命中数、Buff 总量、每秒周期触发数；至少提供一万目标档。固定种子记录查询、结算、Buff 周期、显示、GC/内存和完整帧时间，不能仅用“有一万实体”当技能性能达标。

## 与已有模块及场景的连接

新场景建议名 SkillArchitectureDemo。固定玩家外观、相机、HUD、技能按钮、Buff 面板、说明文字、测试树节点保存到场景/Prefab；高数量目标为 ECS 数据与批量渲染。

现有圆形指示器经适配器消费统一技能范围参数，预览与实际命中共享几何定义和超距策略，避免两套半径。原 CircleSkillPreset 保留其 Demo 用途，不让它持有战斗运行态。新形状对应新增视图，而不是修改效果结算。

技能核心不引用 FogDemoSession；通过目标过滤适配器获取阵营/可见性。独立技能演示默认使用全可见适配器，是否首版联动迷雾另行确认。

新场景的技能目标和系统使用明确的会话/组件筛选，不会因程序集载入就接管 Game 中的单位。未来接入 Game 要统一伤害/属性写入入口，避免旧 CombatSimulationSystem 与新技能系统各维护一套权威血量。本轮建议先验证独立场景，Game 迁移另行确认。

## 建议首版验收范围

建议先用三个圆形技能验证组合复用，技能名称和数值均为临时测试配置：

| 示例 | 组合 | 验证目的 |
| --- | --- | --- |
| Q 爆裂 | 鼠标落点圆 + 即时伤害 + 灼烧 | 即时效果与持续 Buff 分离，伤害/周期共用结算 |
| W 寒霜区域 | 鼠标落点持续圆 + 区域查询 + 减速 Buff | 持续区域投递、刷新/离开/到期规则 |
| E 鼓舞 | 自身中心圆 + 友方过滤 + 加速 Buff | 阵营过滤、同一个属性修正执行器可表达减速与加速 |

可额外选择首版加入扇形、直线弹体和命中爆炸，但这会增加几何、碰撞和展示验收；架构设计可预留，是否实现由用户决定。

必要验收：两个角色共享同一技能配置却拥有独立冷却/Buff；重复 Buff、来源重叠、驱散、到期后属性正确；取消/打断不重复扣费；施法者/目标销毁不遗留引用；连续重开无资源增长；指示范围与命中一致；一万目标压测不承诺尚未测量的帧率。

建议继续沿用已有瞄准习惯：Q/W/E 进入瞄准、左键确认、右键/Esc 取消，超距按已有布尔策略处理。示例技能的消耗、冷却、周期、离开区域残留和升级规则在实施前确定。

## 请用户定夺

1. 是否选择 A：参考 GAS 职责，自建轻量 ECS 核心；或希望先评估第三方完整框架？
2. 首版先用三个圆形技能验证组合，还是立即覆盖扇形/直线弹体？
3. 首版局内升级仅改数值，还是允许替换范围/效果/投递的组合？后者将纳入运行时配置覆盖和合法性验证。

回答技术细节或仅表示某部分偏好不自动代表全面批准。收到明确架构与范围确认后，再收敛示例玩法的剩余关键参数并开始实施。
