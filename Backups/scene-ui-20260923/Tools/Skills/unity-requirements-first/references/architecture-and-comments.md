# Unity 模块、胶水层和代码注释

## 依赖与职责

- 按功能组织 Combat、Benchmark 等模块，模块内区分数据、模拟、表现、装配和 Editor。仅在存在真实依赖边界时拆 asmdef，不预建空层。
- 组合根创建和连接对象、注册和解绑回调、管理生命周期；不放索敌、伤害或 UI 布局算法。避免把原来的大控制器搬进一个万能 Manager。
- ECS 数据和系统不依赖 UI、输入、相机或 Inspector 插件。外围通过有限命令写入模拟，通过小型只读快照读取展示数据；不逐帧复制一万实体给 UI。
- UI 发出用户意图，不直接调用战斗控制器或操作 EntityManager。桥接层负责命令、实体状态与展示数据之间的转换。实体句柄不泄露为 UI 的长期依赖。
- 配置、运行状态和展示资源分开。静态配置不是共享可变战斗状态。World、查询、Native 容器、订阅和生成对象明确由谁创建、谁释放。
- 采用显式依赖传入；当前规模优先手动装配。确有对象生命周期复杂度再考虑托管侧 DI。不要为每个 ECS 实体构造服务对象或注入容器。

## ECS 实现

- 高频工作使用纯数据、Burst 和批量 Jobs；系统按数据职责划分，不机械地一方法一系统。系统顺序与 Job 数据依赖分别声明，不能互相替代。
- 写清结构变化由哪个 ECB、在哪个边界播放，哪些读写要求同步；避免隐藏的逐实体 Complete 和托管调用。
- 模拟逻辑通过显式组件/请求表达，避免每实体事件总线。低频 UI 通知可用小范围回调，订阅与解绑成对。
- 复用根据真实的第二个消费者或明确需求提取；专用机制留在功能模块。提取后必须减少耦合，不能只是增加转发类。

## 注释与编辑器体验

- 类型说明回答“负责什么”；公共边界使用 XML summary，必要时描述输入、输出、单位、错误行为和调用阶段。简单成员无需重复字段名。
- 复杂代码解释“为什么”：算法取舍、排序要求、同步点、所有权和性能边界；修改逻辑同时修正旧注释。避免逐行翻译代码或用注释替代清楚命名。
- Inspector 参数提供中文含义、单位、作用时机（立即/重开后）及边界。保留序列化字段名和 GUID；改名必须处理迁移。
- 自定义编辑器、Handles 和 Gizmos 放 Editor 程序集；第三方属性只用于外围配置和视图。Scene 可视化默认选中才显示，绘制范围、方向和少量统计，不遍历万级实体绘制标签。
- 第三方插件记录来源、固定版本/提交、许可证、依赖、验证和移除方法，不叠装多个互相覆盖的全局 Inspector。

## 场景与 Prefab 优先

- UI 布局、相机、少量主角外观、静态场地和调试辅助节点优先放进场景；有复用或动态实例化需求的整体做成 Prefab。开发者应能在未运行时查看层级、调整布局、替换资源和定位引用。
- 脚本负责状态、行为与模块连接，不用大量 new GameObject/AddComponent/硬编码坐标重建固定界面。动态 UI 从模板或 Prefab 实例化，固定文案、字体、材质及默认外观保存为资源；不要依赖本机字体才能查看场景。
- 高频万级敌人、弹体等保持 ECS/批量实例化；程序化内容或明确性能需求可以例外，写清原因和资源生命周期。不为了场景可见性为一万实体创建 GameObject。
- 使用清楚的节点名、功能分组和序列化引用；缺失必要引用给可定位错误，不悄悄生成替代树。显示状态与业务逻辑分离，重开不重复创建 Canvas/EventSystem 或订阅事件。
- 编辑器生成工具用于首次搭建和明确迁移。重复运行须保留开发者手改布局/引用，不在打开场景、编译或进入 Play 时自动覆盖资源。已有场景对象由场景管理生命周期，运行时只清理自己创建的资源。
- 验收检查编辑状态下可见可修改、进入 Play 无重复节点、重开不增殖、退出不误删资源，并记录修改入口及仍由代码驱动的属性。

## 验证要求

功能重构先记录行为不变量，再核对依赖方向、退出/重开清理、场景引用与序列化兼容，并运行相关逻辑和 Player 检查。插件编译通过与视觉验收分开记录；性能结论仍以目标平台实测为准。
